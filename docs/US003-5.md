# US003-5 — QR na emissão e consulta exclusiva do beneficiário

Branch: `feature/US003-5-gerar-qr-na-emissao-e-consultar-codigo`.

## Ordem de integração

Esta branch foi criada inicialmente na `dev` e recebeu, por fast-forward, os commits de `feature/US003-1-gerar-qrcode-por-procedimento`, conforme combinado. Mesclar a US003-1 antes desta task. Até isso ocorrer, um PR para `dev` também mostrará os commits da US003-1. Para revisar somente esta task, compare com a branch da US003-1; depois selecione `dev` como destino final.

O contrato deste card substitui o GET da US003-1. Há somente uma rota `GET /atendimentos/{id}/qrcode`. Ela deixa de gerar código/imagem na consulta e passa a devolver somente o código previamente salvo, com autenticação, propriedade e sessões completas. Os serviços internos de geração de UUID e imagem da US003-1 continuam disponíveis para integrações próprias.

A autenticação real depende da **US000-16**, ainda ausente na base. O código espera `Principal.getName()` com o login/CPF de `Usuario.login`, relacionado a `Beneficiario.usuarioId`. Confirmar esse contrato ao integrar a US000-16. O perfil normal não confia em `X-Prec-Cp`, parâmetros de requisição ou headers simulados para identificar o dono.

## Emissão e backfill

`CriarProcedimentosDaGuiaService` injeta `GerarCodigoQrService` e preenche `Guia_Proc.QR` antes de salvar cada procedimento, dentro da transação de emissão. O gerador reaproveita `GerarCodigoUnicoQrService` da US003-1, baseado em UUID v4 aleatório. Uma guia com três procedimentos recebe três códigos diferentes. O índice único da V15 protege a exclusividade dos códigos no banco.

A migration `V16__preencher_qr_guias_emitidas.sql` executa o backfill de procedimentos sem QR, ou com QR em branco, nas guias já emitidas. Usa `gen_random_uuid()` nativo do PostgreSQL 16. Não troca códigos existentes, não altera status nem marca sessões como realizadas. O SQL pode ser repetido sem girar os códigos. A migração é executada automaticamente pelo Flyway ao subir a aplicação.

## Consulta

```http
GET /atendimentos/{id}/qrcode
```

Resposta 200, com um único campo:

```json
{"codigo":"a8f3c1d2-7b4e-4c19-9a55-0e1d2f3a4b5c"}
```

O controller usa `dto.request.QrCodeResponse`. `BuscarQrDoProcedimentoService` consulta o dado salvo em uma transação somente de leitura. Não cria QR, não grava e não gera imagem.

A identidade é resolvida antes de consultar o atendimento. `ValidarDonoDaGuiaService` compara o beneficiário autenticado com o `benf_id` da guia antes de verificar status e sessões, para que outro beneficiário receba 403 sem descobrir o estado do procedimento.

| Situação | Resposta |
| --- | --- |
| Sem identidade autenticada | 401 `AUTENTICACAO_OBRIGATORIA` |
| Outro beneficiário ou login sem beneficiário | 403 `BENEFICIARIO_SEM_PERMISSAO` |
| Atendimento inexistente, com beneficiário autenticado | 404 `ATENDIMENTO_NAO_ENCONTRADO` |
| Guia/procedimento expirado ou fora da validade | 409 `GUIA_EXPIRADA` |
| Procedimento REALIZADA ou FATURADA | 409 `PROCEDIMENTO_JA_REALIZADO` |
| Sessões ainda incompletas | 409 `SESSOES_INCOMPLETAS` |
| Código ausente apesar de todas as sessões completas | 409 `QR_NAO_GERADO` |
| Guia/status incompatível com atendimento em aberto | 409 `GUIA_NAO_EMITIDA` |

As quantidades autorizada e realizada seguem os campos mantidos por `RegistrarSessaoService`. Até o procedimento de sessão única precisa ter sua sessão registrada para consultar o código. O QR é apresentado após concluir as sessões e **antes** da baixa final; após a baixa, o status REALIZADA bloqueia novas consultas. Essa ordem concilia a descrição de baixa final com a regra explícita do card que proíbe procedimento já realizado.

A validade continua usando `ValidadeGuiaService`, com 60 dias por padrão, inclusive o último dia. `QrCodeIndisponivelException` aplica 409 somente a esta consulta. As demais rotas de validação e baixa continuam com seus códigos HTTP anteriores, incluindo 422.

## Testar localmente

Para testar sem a US000-16, ative **os dois perfis** `dev,qrconsulta-mock`. O filtro mock só existe com os dois ativos. Ele simula o login com `X-Mock-Login`, mas a autorização continua consultando a associação real no banco. Um Principal real existente nunca é substituído pelo header.

A V17, exclusiva do perfil mock, relaciona dois usuários fictícios aos beneficiários do seed dev e cria uma guia com três códigos:

| Header X-Mock-Login | Beneficiário |
| --- | --- |
| `00000000351` | Dono da guia de teste, Prec-CP `123456789-00` |
| `00000000352` | Outro beneficiário, Prec-CP `111111111-00` |

Em um banco novo com esses seeds, os atendimentos 4, 5 e 6 representam, respectivamente, sessões completas, sessões incompletas e procedimento realizado. O atendimento 3 é antigo e pertence ao segundo beneficiário.

Use um banco exclusivo de desenvolvimento. Não é necessário apagar nem reparar os bancos das branches anteriores. As migrations 13/14 da US000-17 ainda não estão nesta base; um banco com esse histórico não pode ser usado diretamente aqui. Mantenha também os perfis do histórico que já foi aplicado. Não use `qrconsulta-mock` em produção.

Exemplo pela linha de comando, sem alterar o `.env`:

```bash
docker run --detach --rm --name fusex-us0035-dev-db \
  -e POSTGRES_DB=fusex_us0035_dev \
  -e POSTGRES_USER=fusex_test \
  -e POSTGRES_PASSWORD=fusex_test_local \
  -p 127.0.0.1:55435:5432 postgres:16-alpine

SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:55435/fusex_us0035_dev \
SPRING_DATASOURCE_USERNAME=fusex_test \
SPRING_DATASOURCE_PASSWORD=fusex_test_local \
SPRING_DOCKER_COMPOSE_ENABLED=false \
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev,qrconsulta-mock
```

As mesmas variáveis podem ser configuradas em **Environment variables** no IntelliJ, com **Active profiles** `dev,qrconsulta-mock`. Credenciais acima são apenas exemplos locais. Não inicie duas APIs na porta 8080 ao mesmo tempo.

No Postman ou em [`requests/us0035.http`](../requests/us0035.http), use `GET http://localhost:8080/atendimentos/4/qrcode` com `X-Mock-Login: 00000000351`. Troque o login para o segundo beneficiário para confirmar o 403.

```bash
US0035_TEST_DB_URL=jdbc:postgresql://localhost:55435/fusex_us0035_test ./mvnw clean test
```

O teste de integração usa os perfis locais e confirma o retorno restrito, a propriedade, 401/403/404/409, três UUID na emissão real de uma pré-guia, consulta sem geração, backfill idempotente e bloqueio após baixa final. A variável `US0031_TEST_DB_URL` pode habilitar também a regressão dos serviços da US003-1, apontando para **outro** banco de testes sem o seed V17.
