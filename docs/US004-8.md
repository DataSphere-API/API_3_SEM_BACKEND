# US004-8 — Baixa final por QR

Base: `dev` (`e2e01d9`), com autenticação US000-16 e US003-5/6 integradas.

## Contratos

- `POST /atendimentos/validar-qrcode`: recebe apenas `{"qr":"..."}`.
- `GET /atendimentos/qrcode/{codigo}`: não exige mais parâmetro `cnpj`.
- Ambas exigem Bearer token do funcionário OCS. CNPJ é extraído de `UsuarioLogado`.
  Dados extras enviados pelo cliente não mudam a OCS autenticada.
- OCS de outro contrato: 403 `OCS_DIFERENTE_DO_CONTRATO`.
- Procedimento EXPIRADA/EXPIRADO, REALIZADA/REALIZADO ou FATURADA: 409.
- Guia expirada por status ou prazo: 409 `GUIA_EXPIRADA`.
- Sessões incompletas: mantém 422 `SESSOES_INCOMPLETAS` e os detalhes do saldo.

A baixa de uma única sessão ainda não registrada cria `sessao_procedimento` na
mesma transação. Duas baixas simultâneas não duplicam essa sessão.

`RegistrarSessaoService` usa `findByIdParaSessao` com trava pessimista. Cada
sessão válida incrementa o saldo exatamente uma vez e recebe número sequencial.
A primeira transição para EM_ANDAMENTO grava histórico com origem
`registro-sessao`. Guias PARCIALMENTE_REALIZADA podem continuar recebendo sessões.
O corpo legado da rota de sessões foi mantido, mas seu CNPJ não define a OCS:
a autorização e o registro utilizam o funcionário autenticado.

## Ajustes de integração necessários na dev

Foram encontradas dependências de segurança/validação ausentes no POM, códigos
de erro já utilizados mas ausentes no enum, métodos de repositório usados pela
autenticação ausentes e erros pontuais de compilação (import, logger e `}q`).
Essas referências foram restauradas sem alterar o fluxo de faturamento.

Havia duas migrations V13 e duas V15 (esta última colisão aparecia no perfil dev).
A migration de fatura passou para V20 e o seed de usuários para V14.1 (antes dos
seeds opcionais de consulta QR). O cadastro
do chefe continua em V13 e o QR em V15.

**Bancos existentes:** conferir `flyway_schema_history` antes da atualização.
Um banco que já aplicou a antiga V13 de fatura ou V15 de usuários precisa de
reconciliação específica com backup; não executar `repair` nem apagar histórico
indiscriminadamente. Os testes desta task utilizam somente banco descartável.
Nenhum banco existente ou `.env` foi alterado.

## Testes

Usar Java 21+ e PostgreSQL 16. Para criar um banco local descartável:

```sh
docker run --rm -d --name fusex-us0048-dev-db \
  -e POSTGRES_DB=fusex_us0048_verificacao -e POSTGRES_USER=fusex_test \
  -e POSTGRES_PASSWORD=fusex_test_local -p 127.0.0.1:55448:5432 postgres:16-alpine
US0048_TEST_DB_URL=jdbc:postgresql://localhost:55448/fusex_us0048_verificacao \
  mvn clean test -Pvalidacao-us0048
```

O perfil explícito compila/executa a regressão de QR e sessões. O comando padrão
`mvn test` permanece sem exclusões: na base recebida, ele está bloqueado por
`FaturaControllerErrosTest`, que referencia serviços removidos e um construtor
antigo do controller. Essa pendência não foi mascarada nem corrigida nesta task.
Integrações antigas de QR usam variáveis próprias e podem ficar como skipped.

`BaixaFinalQrIntegrationTest` utiliza banco real, login por senha, token e a
cadeia de segurança. Cobre concorrência de sessões, duas baixas concorrentes,
sessão única persistida, OCS errada (inclusive com CNPJ forjado), expiração,
procedimento realizado/faturado, autenticação e bloqueio da cobrança incompleta.
Se `US0048_TEST_DB_URL` não estiver definida, a integração é skipped.

Para testar manualmente, subir a aplicação com perfil `dev`, apontando para esse
banco e porta 8088. Exemplos em `requests/us0048.http`; os QR de teste podem ser
consultados com `SELECT id, qr, status FROM guia_proc ORDER BY id`.

O container foi criado com `--rm`, sem volume persistente: pará-lo descarta
somente os dados locais de teste desta task.
