# US000-17 — Cadastros do chefe e buscas de apoio

Branch: `feature/US000-17-cadastros-chefe-buscas-apoio`, baseada em `dev`.

## Testar no IntelliJ

1. Abra o `pom.xml` do backend como projeto Maven e selecione JDK 21 ou superior.
2. Configure o PostgreSQL conforme o README. Prefira um banco de desenvolvimento separado para os mocks.
3. Na configuração de execução de `FusexApplication`, informe **Active profiles**: `dev,cadastros-mock`.
4. Execute a aplicação e abra [`requests/us00017.http`](../requests/us00017.http).
5. Execute as requisições na ordem do arquivo. Repetir cadastros de OCS, procedimento ou contrato retorna 409.

Alternativa com Maven:

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=dev,cadastros-mock
```

O seed V14 cria dados fictícios para simular o primeiro acesso:

| Login | Prec-CP | Situação |
| --- | --- | --- |
| `00000000001` | `US17-CHEFE` | Chefe autorizado a cadastrar |
| `00000000002` | `US17-MILITAR` | Autocadastro simulado, disponível para receber perfis |
| `00000000003` | `US17-MEDICO` | Médico com CRM `MOCK-US17` |
| Sem login | `US17-PENDENTE` | Deve retornar `PRIMEIRO_ACESSO_PENDENTE` |

Informe `X-Mock-Login: 00000000001` nos POSTs e em `GET /usuarios`. O header só cria um `Principal` quando **dev e cadastros-mock** estão ativos. A autorização consulta o vínculo real do chefe no banco. Sem identificação, retorna 401; sem perfil de chefe, 403.

Não existe endpoint de login mock nesta task. As senhas dos três usuários fictícios são marcadores sem acesso por senha. O cadastro de usuário OCS grava a senha enviada com BCrypt e nunca a devolve na resposta.

O perfil `cadastros-mock` não deve ser ativado em produção. Use o mesmo banco sempre com os perfis correspondentes às migrations que já foram aplicadas; o Flyway valida o histórico dos seeds.

Esse perfil habilita `spring.flyway.out-of-order=true` para carregar a V12 também em bancos locais que já receberam a V13. Não é necessário adicionar esse argumento no IntelliJ nem recriar o container. A V14 ajusta os contadores de médicos e chefes após os IDs explícitos do seed.

## Endpoints

| Método | Rota | Resposta |
| --- | --- | --- |
| GET | `/ocs` | `{"ocs":[{"cnpj":"...","nome":"..."}]}` |
| POST | `/ocs` | OCS criada, 201 |
| GET | `/procedimentos` | `{"procedimentos":[{"id":1,"nome":"..."}]}` |
| POST | `/procedimentos` | Procedimento criado, 201 |
| GET | `/contratos` | `{"contratos":[{"id":3,"ocsCnpj":"...","ocsNome":"...","procedimentoId":10,"procedimentoNome":"...","valor":720.49}]}` |
| POST | `/contratos` | Contrato criado com os mesmos campos, 201 |
| GET | `/usuarios` | `{"usuarios":[...]}`, restrito ao chefe |
| POST | `/usuarios` | Usuário OCS criado ou perfis do militar acrescentados, 201 |
| GET | `/medicos` | `{"medicos":[{"id":4,"nome":"Maria","crm":"12345"}]}` |
| GET | `/beneficiarios?busca=` | `{"beneficiarios":[{"precCp":"...","nome":"...","dataNascimento":"1986-05-10","dependente":false,"ug":"2ª Bda"}]}` |

A busca combina nome (sem diferenciar maiúsculas) ou Prec-CP, ordena por nome e Prec-CP e limita no banco a 20 resultados. Busca vazia também respeita o limite; `%` e `_` são tratados como texto pelo Spring Data.

OCS e CPF são normalizados removendo pontuação usual e espaços. Nome de procedimento é único sem diferenciar maiúsculas ou espaços nas extremidades. Contratos aceitam valores positivos de até `99999999.99`, com no máximo duas casas decimais significativas. Senhas de usuários OCS têm de 8 caracteres a 72 bytes, limite compatível com BCrypt.

As constraints da V13 protegem duplicidades mesmo em acessos concorrentes. Se já existirem nomes de procedimentos ou pares procedimento/OCS duplicados no banco, a migration falhará para preservar os registros e exigir saneamento explícito.

## Integração com US000-16

O cadastro de militar usa `Beneficiario.usuarioId` para confirmar que o autocadastro já ocorreu. Acrescenta os perfis `CHEFE`, `MEDICO`, `EMISSOR` e `AUDITOR` nas tabelas existentes, preservando os anteriores. `EMISSOR` corresponde a `Analista`.

O contrato provisório usa `Usuario.login` como CPF e espera que `Principal.getName()` contenha esse login. Quando a US000-16 chegar, alinhar esse identificador, o `UsuarioModel`, a codificação de senhas e a numeração das migrations com a implementação de autenticação da equipe. Até essa integração, o fluxo pode ser testado com os mocks acima; o perfil normal exige um `Principal` real e não aceita `X-Mock-Login`.

O frontend permanece usando sua camada de mocks existente. Esta task implementa os endpoints do backend; a integração HTTP das telas deve consumir os objetos de listagem descritos na tabela.

## Testes

```bash
# Testes existentes e verificação de que o filtro mock depende dos dois perfis
./mvnw test

# Integração: somente em um PostgreSQL exclusivo para testes, vazio na primeira execução.
# Credenciais esperadas: fusex_test / fusex_test_local.
US00017_TEST_DB_URL=jdbc:postgresql://localhost:55417/fusex_us00017_test ./mvnw test
```

Os testes de integração aplicam as migrations, exercitam os controllers e consultam o banco para verificar os registros. Incluem uma operação fora da transação de teste para confirmar o commit, além de cenários de autorização, duplicidade, valor, usuários, hash de senha e limite da busca. Sem a variável de ambiente, esses testes são ignorados.
